CRCE · cómo se construyó el modelo

1 · Leemos el enunciado y marcamos lo importante

Enunciado · §1 Descripción del negocio

El CRCE es un organismo encargado de organizar la respuesta ante situaciones que ponen en riesgo a personas, bienes e infraestructura. Recibe avisos sobre inundaciones, incendios y accidentes viales, a partir de los cuales sus operadores evalúan las situaciones, registran las emergencias que requieren intervención y organizan las misiones necesarias para atenderlas.

El CRCE dispone de bases operativas donde se encuentran unidades de respuesta integradas por personal especializado, vehículos y equipamiento. No todas las unidades cuentan con las mismas capacidades.

2 · Reglas del aviso

Enunciado · §7.1 Avisos

Los avisos comienzan pendientes de evaluación. Un operador puede aceptar un aviso y originar una emergencia, o descartarlo registrando una justificación. Un aviso aceptado origina una única emergencia y no puede evaluarse nuevamente; uno descartado tampoco puede ser aceptado posteriormente.

3 · Reglas de la misión

Enunciado · §8.1 Estados de misión

Cada misión atraviesa los estados: Pendiente, Asignada, En ejecución, Finalizada y Cancelada.

No se admiten transiciones arbitrarias entre estados, y una misión finalizada o cancelada no puede reabrirse.

4 · Reglas de la asignación

Enunciado · §8.2 Asignaciones

El operador selecciona una unidad completa. El sistema verifica que exista una distribución de personas distintas que cubra los requisitos de la misión.

Antes de confirmar verifica: emergencia abierta, misión pendiente (o asignada si se reasigna), unidad disponible y habilitada, sin otra misión, vehículo compatible y operativo, personal y competencias y equipamiento necesario.

Si alguna condición no se satisface, la asignación se rechaza indicando el motivo.

6 · El sistema contado como una historia

  • Llega un aviso («se inundó la calle Mitre»). Un operador lo acepta y nace una emergencia, o lo descarta explicando por qué.
  • Dentro de la emergencia se crean misiones: evacuar, rescatar o dar asistencia sanitaria. Cada tipo sirve solo para ciertas situaciones.
  • A cada misión se le asigna una unidad completa (jefe, gente, vehículo y equipo). Antes se revisa que sirva: si algo falla, no cambia nada y se dice el motivo.
  • El jefe de la unidad inicia la misión, anota novedades y la finaliza. La emergencia se cierra cuando todas sus misiones terminaron y al menos una salió bien.
  • Regla del profesor: nunca preguntar «¿de qué clase sos?» (isinstance). Cada objeto responde por sí mismo (eso es polimorfismo).

7 · Palabras de diseño que se repiten (glosario)

  • Entidad: algo con identidad propia que cambia con el tiempo. Un aviso sigue siendo «el mismo aviso» aunque pase de pendiente a aceptado.
  • Objeto valor: un dato que vale por su contenido y no cambia nunca, como una dirección. Dos «Mitre 100, Rosario» son la misma.
  • Patrón State: en vez de guardar el estado como texto y llenar todo de if, cada estado es un objeto que sabe qué se puede hacer y qué no.
  • Herencia y polimorfismo: las clases hijas comparten lo de la madre. Si a todas les pedís lo mismo, cada una responde a su manera.
  • Doble despacho: la misión le pregunta al vehículo «¿servís para esto?» y el vehículo contesta según su tipo. Nadie usa if para averiguar el tipo del otro.
  • Null Object: en vez de None («no hay nada»), un objeto que representa «sin unidad» y responde sin romper. Así no hace falta preguntar if unidad is None.
  • Raíz de agregado: el objeto «encargado» de un grupo. Para tocar una misión se pasa por su emergencia; para tocar los recursos, por la flota.
  • Fallar antes de modificar: primero se revisa todo lo que puede salir mal y recién después se cambia algo. Un error nunca deja las cosas a medias.

8 · Python que aparece todo el tiempo (machete)

  • _nombre (guion bajo adelante): «es interno, no se toca desde afuera». Python no lo prohíbe; es un acuerdo entre programadores.
  • @algo arriba de una función o clase es un decorador: le agrega un comportamiento. Los que vas a ver: @dataclass, @property, @classmethod, @abstractmethod.
  • @property: un método que se lee como un dato, sin paréntesis (aviso.estado, no aviso.estado()), y que no se puede asignar.
  • : str, -> None, str | None: anotaciones de tipo. Son carteles para quien lee; Python no las controla. str | None = «un texto, o nada».
  • x is None, x is Gravedad.ALTA: is pregunta «¿es exactamente el mismo objeto?». Se usa con None y con los valores de los catálogos.
  • pass y ...: «no hacer nada». pass en un método significa «permitido, sigo»; ... en un método abstracto significa «esto lo escribe cada hija».
  • raise Error("motivo"): corta la operación y avisa qué salió mal. Quien llamó puede atajarlo con try / except.
  • *, en los parámetros: todo lo que viene después se pasa con nombre (restaurar(aviso_id="a1", ...)). *algo y **algo juntan «cualquier cantidad» de valores.
  • from __future__ import annotations (primera línea de casi todos los archivos): permite nombrar en las anotaciones una clase que se define más abajo. No cambia lo que hace el programa.
  • f"Falta {x}": texto con huecos que se llenan con valores. {x!r} muestra el valor «crudo» (con comillas si es texto).

13 · Por qué la Ubicación no se puede modificar

Situación

Entra un aviso en «Mitre 100, Rosario». Al aceptarlo se crea la Emergencia con esa misma ubicación: el aviso y la emergencia comparten el mismo objeto, no una copia.

Sin esta decisión (ejemplo hipotético) · Sin frozen: una ubicación que se puede editar
class UbicacionMutable:
    def __init__(self, direccion, localidad):
        self.direccion, self.localidad = direccion, localidad

u = UbicacionMutable("Mitre 100", "Rosario")
ubicacion_del_aviso = u
ubicacion_de_la_emergencia = u      # comparten el mismo objeto
ubicacion_del_aviso.localidad = ""  # alguien edita el aviso y borra la localidad
print(repr(ubicacion_de_la_emergencia.localidad))
''
Qué sale mal

Editar el aviso cambió también la emergencia, sin pasar por ninguna validación. La emergencia queda sin localidad y la unidad no sabe adónde ir. Y es un error muy difícil de rastrear: nadie tocó la emergencia.

Con el proyecto (código real) · Con frozen: el intento falla en el acto

u.localidad = 'Salta'

Situación

¿Y si de verdad hay que corregir la localidad? Se crea otra ubicación; las que ya existían no se tocan.

Con el proyecto (código real) · Corregir = crear una nueva, validada

Cómo se lo explico al profesor

No quiero que se modifique porque la ubicación se comparte entre el Aviso y la Emergencia: si alguien la cambiara en un lado, cambiaría en los dos y sin validar. Al ser inmutable se valida una sola vez, al crearla, y desde ahí es válida para todos los que la usan.

14 · Para qué sirve slots

Situación

Alguien escribe mal el nombre de un campo al querer corregir un dato (localidd en vez de localidad).

16 · Los errores, por arriba

  • Cuando una regla no se cumple, el programa lanza un error con nombre propio (por ejemplo JustificacionVacia) y no cambia nada.
  • Todos están en errores.py y heredan de ErrorDeDominio: se pueden atajar todos juntos o uno en particular.
  • Están agrupados por tema: avisos, recursos, asignación, misiones, emergencias e historial. El nombre ya dice qué pasó.
  • Algunos son de la misma familia: UnidadOcupada, VehiculoIncompatible, PersonalInsuficiente… son todos AsignacionRechazada, cada uno con el motivo exacto (§8.2).

19 · Por qué el estado decide y no un if

Situación

§7.1: un aviso descartado ya no puede recibir notas. Con un campo estado de texto, cada operación del Aviso tendría que acordarse de revisarlo.

Sin esta decisión (ejemplo hipotético) · Sin State: un `if` en cada operación
class AvisoConIf:
    def __init__(self):
        self.estado = "descartado"
        self.notas = []
    def aceptar(self):
        if self.estado != "pendiente":
            raise ValueError("ya no está pendiente")
    def agregar_nota(self, texto):        # acá nos olvidamos el if
        self.notas.append(texto)

a = AvisoConIf()
a.agregar_nota("llegó tarde")
print(a.estado, a.notas)
descartado ['llegó tarde']
Qué sale mal

Un descartado aceptó una nota. Con diez operaciones y cinco estados, olvidarse un if es cuestión de tiempo y el sistema no avisa.

Con el proyecto (código real) · Con State: es el estado quien responde
from datetime import datetime
from dominio.aviso import Aviso
from dominio.catalogos import Gravedad, TipoSituacion
from dominio.valores import Ubicacion

aviso.agregar_nota("rep1", "llegó tarde", ahora)

Cómo se lo explico al profesor

Cada estado es una clase que sabe qué admite. El Aviso no pregunta «¿qué estado sos?»: le pasa la operación y el estado responde. No hay un if que se pueda olvidar, y preguntar el tipo con if rompe con POO: cada objeto debe responder por sí mismo.

def alcanza_rapido(puestos, personas):
    libres = list(personas)
    for puesto in puestos:
        elegida = next((p for p in libres if puesto in p[1]), None)
        if elegida is None:
            return False
        libres.remove(elegida)
    return True

bruno = ("Bruno", {"conduccion"})

Qué sale mal
